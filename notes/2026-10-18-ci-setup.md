# Lab log — 2026-10-18 — CI setup (and why the PR showed "failed")

## Symptom

PR #3 showed a failing check.

## Root causes (two, independent)

1. **GitHub Actions is billing-locked.** Every job failed to start with:
   *"The job was not started because your account is locked due to a billing issue."*
   This is **account-level** and has nothing to do with the code, the workflow, or the tests.

2. **CircleCI couldn't find its config.** Error:
   *"config file `.github/workflows/ci.yml` could not be located in feat/indic-eval-suite-v1"*.
   This project's CircleCI setup uses the preview feature **"Use a GitHub Actions workflow file
   as your pipeline configuration"**, pointed at the path `.github/workflows/ci.yml`. My branch
   had named the workflow `validate.yml`, so CircleCI found nothing.

## Fixes

- **Renamed the workflow to `.github/workflows/ci.yml`** — a single file that serves *both*
  GitHub Actions and CircleCI (this matches the convention on the existing experiment branches).
- **Dropped `actions/setup-python`.** CircleCI's GitHub Actions mode disables the `add-path`
  workflow command that setup actions rely on, so it would succeed *without taking effect*. The
  suite needs only Python 3.10+, which the runner image provides.
- **Removed the redundant `.circleci/config.yml`** (single source of truth for CI).
- **Disabled the GitHub Actions workflow** (`gh workflow disable`) so the billing lock stops
  producing a spurious red X on PRs. CircleCI does the validating meanwhile.

## Result

- ✅ `ci/circleci: validate` — **pass** (CircleCI runs `python3 validate.py` +
  `python3 evaluate.py --backend mock --langs hi`).
- ⏸️ GitHub Actions — disabled (not deleted; the file is intact).

## To restore GitHub Actions later

1. Fix the billing issue: GitHub → **Settings → Billing & plans**.
2. Re-enable the workflow: `gh workflow enable CI`, or Actions tab → *Enable workflow*.
3. Re-enable the leftover `validate` workflow only if you want it; its file no longer exists.

## Lesson

More than one CI system can read the *same* workflow file. When two are connected, the file's
**path and name are load-bearing** — a rename that looks cosmetic silently breaks the other system.
The constraint is now documented at the top of `.github/workflows/ci.yml`.
